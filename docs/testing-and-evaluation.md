# 测试与 RAG Evaluation 设计

第 1–7 节为分阶段测试与评测策略；阶段 2/3/4 的已实现测试分别见第 8/9/10 节。当前无 RAG 质量评测结果。

## 1. 验证层次

| 层 | 工具/依赖 | 验证对象 | 不能据此宣称 |
| --- | --- | --- | --- |
| 单元 | pytest；测试内模型/存储替身 | 权限组合、Chunking、状态规则、预算、引用映射 | 真实数据库或模型已接通 |
| 接口契约 | pytest + HTTP 客户端 | 请求响应、错误码、SSE 终态 | 真实模型质量已达标 |
| 服务集成 | pytest + 真实 MySQL/Qdrant 测试实例 | 迁移、事务锁、租约、向量写读、Filter | Embedding/LLM 供应商正常 |
| 真实 AI 验证 | 独立 live 标记 + 已配置真实 API | 实际 Embedding、流式 LLM、维度、来源与超时 | 离线测试替身的输出等同模型能力 |
| UI 关键行为 | 前端类型检查、构建及必要组件测试 | SSE 分包、Markdown 安全、任务/断流状态 | 仅通过构建就完成端到端验收 |
| RAG 评测 | 真实语料、人工标注、相同服务路径 | 检索与回答质量、引用、拒答、耗时 | 一个综合分数足以证明全部能力 |

业务单元测试允许可控替身，用于隔离规则及注入失败；禁止在生产或演示配置中以这些替身提供“成功”答案。集成测试必须说明向量来源：测试规则可用明确的测试向量，但真实端到端验收必须使用真实 Embedding。

## 2. 必须覆盖的关键场景

| 领域 | 必测规则 |
| --- | --- |
| 身份/成员 | 无效 token、停用用户、角色边界、最后有效 owner、并发 owner 删除/降级 |
| 资源隔离 | 跨库文档/任务/文件/Chunk/会话 ID；会话属于其他用户；筛选不能扩大范围 |
| 上传/解析 | 大小限制、扩展名与实际格式、路径穿越、空正文、扫描 PDF、页码/字符定位 |
| Chunking | 中文分隔符、配置非法值、边界覆盖、目标 overlap、稳定 ordinal 和定位；不照抄实现做无意义断言 |
| 任务 | 单次领取、多 Worker 竞争、续租、超时回收、次数上限、永久错误、手动重试冲突 |
| 版本/幂等 | 批次重复 upsert、迟到 Worker、部分写入、发布前崩溃、发布后响应丢失、重建失败保留旧版本 |
| 删除/清理 | 逻辑删除即时阻止检索；Qdrant 故障时可重试清理；迟到写入只形成不可检索孤立版本 |
| 检索 | Top-K 校验、空授权集合、强制版本过滤、Metadata AND 组合、正文复核、有限补召回、profile 不匹配 |
| RAG | 多轮只用合法成功历史、预算超限、无上下文拒答、未知引用、来源与 Chunk 对应 |
| SSE | 正常事件顺序、UTF-8/事件分包、流内错误、心跳、断开取消、数据库最终提交失败、EOF 无终态 |
| 会话并发 | 相同 client_request_id 不重复生成、不同请求同时只有一个生成槽、超时遗留槽回收 |
| 观测/超时 | 日志脱敏、request_id 一致、有限重试、首 token 后不重启生成、总 deadline 不被心跳延长 |

Hybrid/Rerank 阶段补测各分支过滤、融合排名/去重、候选裁剪、真实 rerank 输出映射及显式降级。权限测试必须检查“送入模型或 Rerank 的正文”，不仅检查最终回答字符串。

## 3. 测试执行和隔离

- 后续定义 unit、integration、live 标记；默认开发/CI 执行不收费的 unit + 配置好的服务集成，live 独立显式启用。
- CI 不持有真实模型密钥；若只运行 unit 必须明确报告，不能把未运行 integration/live 写成通过。
- MySQL 使用专门测试 database，Qdrant 使用独立测试 collection 和文件临时目录；测试前检查测试环境标识，不能清空业务库或共享 collection。
- 不用 SQLite 测试结果替代 MySQL `SKIP LOCKED`、CHECK、复合 FK、JSON 和迁移行为。
- 用确定性的同步屏障制造竞争或崩溃窗口；轮询有短且明确 deadline，避免长时间 sleep 导致脆弱测试。
- 基础迁移测试在空库执行到 head，并验证重复启动不重复执行迁移。
- 只对关键逻辑写有意义的测试；不为纯展示文案或简单样式改动堆测试。覆盖率作为缺口提示，不单独代表正确性。

## 4. 评测题集

阶段 5 建立至少 30 个人工标注问题，来自真实、获授权语料：建议 16 个单轮可回答问题、6 组多轮追问的末轮问题、8 个证据不足/无答案问题。另设独立权限攻击测试集，不混入质量平均分。

每条记录包括：

- case_id、语料/题集版本、用户授权范围、目标知识库逻辑标识。
- question、可选 history、answerable 标记、reference_answer 和可接受关键事实。
- 证据文件 SHA-256、页码/标题/片段，或无答案理由。
- 检索 metadata filter、相关证据及必要时的分级相关性标签。

标注应在观察模型输出前完成，不根据当前系统答案修改“标准答案”。多轮样本的 history 来源于真实语料或人工设定的问句，不能提交私有会话。Chunk UUID 会随索引版本变化，所以题集用稳定源定位，在运行时解析映射。

按能力类型固定开发集与留出集；初版 30 题可采用 20/10 分层划分。配置调优只用开发集，最终报告同时列全题集和留出集。30 题只能形成演示基线，不能证明企业全场景表现。

## 5. 指标和定义

| 指标 | 定义/用途 |
| --- | --- |
| Evidence Recall@K | Top-K 命中的标注证据单元数 / 总标注证据单元数；只对 answerable 样本计算 |
| Hit@K | Top-K 至少命中一个相关证据的问题比例；不能把此指标叫完整 Recall |
| MRR@K | 第一个相关结果排名倒数的均值；未命中为 0 |
| nDCG@K | 基于人工分级相关性计算；没有分级标注时不伪造 nDCG |
| 引用有效率 | 实际引用中能解析到本轮授权候选且来源可核验的比例；未输出引用不能算 100% |
| 事实支持率 | 人工判定回答中的可验证关键事实被引用证据支持的比例 |
| 答案正确率 | 依据预设关键事实和人工 rubric 判定，不以字符串完全相等评价自然语言 |
| 拒答 precision/recall | 拒答是否恰当及无答案问题是否被拒答，分别报告避免“全部拒答”高分 |
| 数据泄漏 | 不授权正文/定位进入任意召回输出、Rerank 或模型上下文的次数；目标必须为 0 |
| 延迟 | 检索、改写、首 token、完整响应的 p50/p95，区分阶段及失败样本 |
| 使用量 | 实际模型调用次数、供应商返回 token；费用只在有真实计价及 usage 时计算 |

权限门槛是独立硬约束，不能用平均检索质量抵消泄漏。拒答率、来源存在性和事实支持属于不同指标，分别报告。

## 6. MVP 初始验收门槛

在固定题集和 Top-K=5 的真实基线上，预先采用以下项目目标；这些是待测目标，**不是当前成绩**：

- 权限攻击、删除残留和迟到版本测试的泄漏为 0。
- Evidence Recall@5 ≥ 0.80；报告样本数与原始命中数。
- 实际输出引用的有效率为 1.00，且需要证据的回答都有引用。
- 人工答案正确率和事实支持率均 ≥ 0.80。
- 无答案问题拒答 recall ≥ 0.875（初版 8 题至少 7 题），同时报告误拒答数量及拒答 precision。
- 记录同机同供应商 p50/p95，阶段 5 依据首次真实试跑约定展示环境的延迟预算，再在优化前固定预算；不在未测网络/模型情况下宣称固定秒数 SLA。

若质量未达标，先检查语料解析、证据标注、Chunking、Prompt 与引用处理，修复并保留前后报告，不能删掉失败题来“通过”。

## 7. 实验可复现性与后续优化

每次报告记录 Git revision（尚未有 Git 时明确为空）、Python/依赖版本、模型供应商与标识、真实索引/profile、Chunk 配置、Prompt 哈希、题集哈希、检索/rerank 配置、随机参数、执行时间和失败数。只存必要实验数据，私有正文与运行产物默认不提交。

Dense、Hybrid、Hybrid + Rerank 使用同一语料、权限与题集；控制最终 Top-K 和上下文预算，单独记录候选数量、配置、额外耗时及调用量。开发集调参，留出集评估；尽量重复运行报告波动。先给出逐题差异，再给汇总指标。

LLM-as-judge 可在后续作为辅助，记录 judge 模型、评分提示和与人工标注的一致性；不能把 judge 分数当作绝对事实，也不能仅因引入 Rerank 就宣称检索效果提高。

## 8. 阶段 2 已实现的测试边界

- `backend/tests/unit`：16 项配置、脱敏、request_id、统一错误、健康状态、OpenAPI 与 Qdrant 故障注入测试。替身只出现在测试代码。
- `backend/tests/integration`：真实 MySQL 基线迁移/回退/重复 upgrade、utf8mb4/UTC、真实 Qdrant 鉴权及专用 collection 写读删除。必须有 `ALLOW_TEST_DATABASE=1` 且 database 以 `_test` 结尾；不接受 SQLite。测试前只允许无业务表的阶段 2 测试库。
- `frontend/tests`：3 项 503/非法报告、网络故障、自动刷新和卸载清理行为测试；另执行 vue-tsc 与 production build。
- `scripts/verify_stage2.py`：独立 Compose 项目验收，分别停止依赖验证 ready=503/live=200，再恢复；强制重建数据容器并读回专用记录验证命名卷；比对 OpenAPI，扫描本次配置的密钥是否进入日志或静态资源。
- 默认 pytest 只运行 unit，显式排除 integration/live；集成结果和真实命令详见 [阶段 2 交付记录](stage-2-delivery.md)。当前没有模型测试、业务并发锁测试或 RAG 质量成绩，后续随各阶段补充。

## 9. 阶段 3 身份与知识库测试

- 单元覆盖 Argon2 成功/失败与密码策略、JWT 签名/算法/claims/过期、用户名规范化、滑动窗口限流、签名游标和配置脱敏。前端覆盖登录/退出、token 不持久化、viewer 隐藏成员管理、owner 拒绝提示、401 清会话和迟到响应隔离。
- 真实 MySQL 集成覆盖三种身份（含无隐含权限的 admin）、私有库隔离、viewer/editor/owner 边界、逻辑删除父资源、停用和撤权后的旧 JWT、分页范围、CLI 用户创建/停用/启用、CHECK/FK/迁移及 utf8mb4/UTC。
- 使用同步屏障并发执行两名 owner 的自我降级、自我移除、同时停用、停用与降级混合竞争；必须恰好一项成功，另一项 LAST_OWNER_REQUIRED，最后仍有一个有效 owner。独立连接持有真实 guard 行锁，通过 SQLAlchemy 执行事件同步等待，验证写事务阻塞和锁后重新检查用户状态，不靠长 sleep 制造竞争。
- 测试仅允许显式开启的 *_test 数据库。fixture 创建随机用户名/UUID，结束按自己拥有的 ID 清理；迁移回退先检查业务表没有记录，不能清空用户数据来通过测试。
- `scripts/verify_stage3.py` 复用骨架故障/卷检查，并通过真实 CLI、Nginx 与 HTTP 验证双账号登录、列表/详情隔离、角色边界、撤权、停用及逻辑删除。临时密码/JWT 加入日志脱敏与密钥扫描，结束清理本次创建的资源。
- 最终结果、浏览器实测和限制见 [stage-3-delivery.md](stage-3-delivery.md)。当前仍无模型、索引、文档和 SSE 测试，不将身份权限通过描述为 RAG 可用。

## 10. 阶段 4 测试范围

真实 MySQL/Qdrant integration 与真实供应商 live 分开报告。单元覆盖模型响应数量/索引/维度/非有限值/零向量、瞬时和永久错误、空范围不查询、中文切分及定位、检索输入白名单。集成覆盖上传/权限/大小/配额/回收、复合 FK、并发领取、SKIP LOCKED、实际续租、过期 token/总 deadline 拒绝、有限重试/后继竞争、独立 Worker SIGKILL 恢复、原版本保留、扫描 PDF、缺点修复、共享 collection 隔离与模型调用中撤权。

`live` 使用真实免费 BAAI/bge-m3，验证中文、文字 PDF 页码、重复 upsert 和撤权/删除；测试语料为测试中生成的公开无敏感内容，不发送私有资料。真实 Nginx/CLI 网络脚本另验证上传、来源、原文件、共享卷重建、删除残留和 Key 不进入日志/静态资源。前端测试覆盖 multipart、内存 token、任务终态停止轮询、只读边界、失败/重试冲突及卸载。

最终执行结果及未验证项见 [stage-4-delivery.md](stage-4-delivery.md)。没有 LLM、SSE 或问答质量评测结果。
